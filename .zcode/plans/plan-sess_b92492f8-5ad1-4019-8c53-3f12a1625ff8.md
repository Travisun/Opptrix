# Extension Platform Phase A — Product-Grade Implementation Plan

## Context

The design docs (EXTENSION-PLATFORM-ARCHITECTURE.md v2.5 + EXTENSION-PLATFORM.md, 2600+ lines, 16 ADRs) describe a comprehensive extension platform. The current implementation is a "thin-A" prototype: in-memory only, callGate just echoes, no real capabilities, no persistence, no R0/R1 lifecycle. This plan delivers **Phase A MVP to product grade**, executable as **8 work packages**, each independently submitted + tested + accepted.

**Confirmed decisions:**
- **ADR-02 amendment**: shared `worker_threads` + `vm` sandbox + multi-layer compensation (capability gate + per-extension storage isolation + resource limits). Process isolation infeasible due to external deployment + route registration; we compensate with stronger vm/gate/storage layers.
- **Scope**: Phase A only (capabilities: storage, llm, sessions.read, data.query, shell, schedule, events; contributions: views, read-only hooks, routes; .opx install; CLI; SDK; sample extension).
- **Delivery**: per-package submit → test → accept → rework cycle.

---

## Package 0: Foundation — ADR-02 Amendment & Capability Registry

**Deliverables:**
- `docs/EXTENSION-PLATFORM-AADR-02-AMENDMENT.md` — document the shared-worker decision, trade-off analysis (process isolation vs shared worker), and the 5 compensation layers: (1) vm sandbox, (2) capability gate + permission enforcement, (3) per-extension storage isolation, (4) resource limits/timeouts, (5) audit logging.
- Bump `PLATFORM_ABI_VERSION` from `0.8.52-thin-a` → `0.9.0-phase-a`.
- `capability-token-registry.ts` — single source of truth mapping capability tokens → required permission + handler + pack. Tokens: `storage.*`, `llm.*`, `sessions.read`, `data.query`, `shell.*`, `schedule.*`, `events.subscribe`, `events.emit`, `platform.info`.
- Update `ExtensionManifest` type: add `permissions[]` (replaces/augments `capabilities[]` for Phase A), `contributes` (hooks/routes/views), `activationEvents`.

**Acceptance:** doc reviewed; ABI bumped; registry exports all Phase A tokens; tests pass.

## Package 1: Persistence + R0/R1 Lifecycle

**Deliverables:**
- Extension records persisted to SQLite (user-store namespace `ext:extensions` or dedicated `extensions.db`); survive restart.
- `activate()`/`deactivate()` persist state transitions.
- **R0 compliance:** startup Phase 0 (core listen) → Phase 1 (async scan) → Phase 2 (activate enabled). `bootstrap()` in index.ts must NOT await extensions. `/api/health` independent.
- **R1 compliance:** wire `extensionShutdownPhase` into `sidecar-shutdown.ts` between `stopSchedulers` and `closeBrowsers` (lines 112/113). Enter draining → emit `app.shuttingDown` → deactivate active extensions (parallel, per-ext 2s timeout) → flush plugin-storage → emit `app.shutdown`. Budget: `min(5000, forceExit×0.4)`.
- `bootScan()` loads persisted records, clears stale error states.

**Acceptance:** server restart preserves extension state; `/api/health` 200 with crashed extension installed; shutdown completes within forceExit budget even with hung extension. R0/R1 integration tests.

## Package 2: Capability Routing & Permission Enforcement

**Deliverables:**
- `callGate()` routes to real services via the registry, not echo. Each token's exec thunk calls the actual adapter:
  - `storage.*` → `PluginStorageService` (per-extension KV)
  - `llm.*` → `LlmProvider` (chat/completions via agent broker)
  - `sessions.read` → `SessionStore` (read-only session access)
  - `data.query` → `queryInstrumentData` (via Engine)
  - `shell.*` → `ShellRunner` (sandboxed, thin)
  - `schedule.*` → `ScheduleService` (job kind registration)
  - `events.subscribe/emit` → `EventDispatcher`
  - `platform.info` → deployment + pack snapshot
- **Permission enforcement**: `PolicyProxy` checks `manifest.permissions[]` contains the required permission for the token before exec. Missing → denial `permission_denied`.
- Audit: every extension capability call logged with `{auditId, pluginId, token, ok, denialCode}`.
- Resource limits: per-extension concurrent RPC cap (default 16), token rate limits.

**Acceptance:** each Phase A capability invokable through `callGate` with correct result; permission-denied returns structured denial; audit log populated; exceeding limits returns `quota_exceeded`.

## Package 3: Per-Extension Storage (Tier 1)

**Deliverables:**
- Wire `SqlitePluginKvStore` per extension (via `plugin-storage` package, already exists).
- `storage.get/set/delete/keys/transaction` scoped to `plugin-data/{pluginId}/`.
- 64MB quota enforcement (already in plugin-storage).
- `exportPlugin`/`importPlugin` for uninstall data portability.
- Storage auto-created on extension activate, flushed on deactivate.

**Acceptance:** extension A cannot read extension B's storage (isolation test); quota exceeded returns clean error; export/import round-trips; uninstall offers data export.

## Package 4: Hooks & Route Contributions

**Deliverables:**
- **Hook infrastructure**: `hook/register` + `hook/dispatch` with timeout (100ms default, configurable), priority ordering, waterfall merge for `agent/toolPreExecute`, abort support.
- **Phase A read-only hooks**: `session/messageCommitted` (observe), `agent/toolPreExecute` (audit-only, no mutate).
- **Route contributions**: `contrib/register` → mount `/api/ext/{pluginId}/*` via Fastify, proxied to extension Host RPC. Auto-cleanup on deactivate.
- Contribution lifecycle: activate registers, deactivate unregisters (routes, hooks, event listeners, job kinds).

**Acceptance:** extension can register a hook that observes session messages; hook timeout doesn't block turn; route `/api/ext/{id}/hello` reachable; deactivate cleans up all contributions.

## Package 5: .opx Install & HTTP API

**Deliverables:**
- Real HTTP route handlers (replacing admit-only diagnostics):
  - `POST /api/platform/extensions/install` — upload .opx (raw bytes) → parse → validate → persist → activate.
  - `POST /api/platform/extensions/:id/activate|deactivate`
  - `DELETE /api/platform/extensions/:id` — uninstall + optional data export.
  - `GET /api/platform/extensions` — list with state.
  - `GET /api/platform/extensions/:id/storage/export` — export data.
- `.opx` install flow: upload → `parseOpxManifestFromZip` → validate manifest + permissions → persist record → create storage → activate.
- Dev mode: `OPPTRIX_EXT_DEV=1` skips signature (signature validation deferred to Phase B).
- Input validation + size limits (2MB zip).

**Acceptance:** upload a real .opx → extension active + reachable; invalid zip rejected with clean error; uninstall removes routes/hooks/storage; list reflects state.

## Package 6: SDK (@opptrix/extension-sdk) & CLI (opptrix-ext)

**Deliverables:**
- `packages/extension-sdk/` — TypeScript SDK:
  - `ExtensionHostContext` type (activate/deactivate signature, callGate, contributions API).
  - `contributions` helpers: `registerHook`, `registerRoute`, `registerView`, `registerJobKind`.
  - `storage` typed wrapper, `events` subscribe/emit, `llm` chat helper.
  - Manifest type for `opptrix.plugin.json`.
- `packages/opptrix-ext/` (or `scripts/opptrix-ext.mjs`) — CLI:
  - `create <name>` — scaffold template extension (manifest + host entry + README).
  - `build` — bundle host entry (esbuild/tsup) + UI (Vite MF).
  - `pack` — produce .opx (zip + checksums).
  - `doctor` — validate manifest, check permissions, size, shared contracts.
  - `compat` — print engines vs host compatibility.

**Acceptance:** `opptrix-ext create demo` produces a buildable extension; `build` + `pack` produce a valid .opx; `doctor` catches manifest errors; SDK types compile.

## Execution Strategy

- **R7 multi-agent orchestration**: Packages 2-6 each get 1 Implementer + 1 Verifier subagent; main agent integrates, audits, accepts.
- **Order**: 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 (strict dependency chain; each builds on prior).
- **Per-package gate**: `npm run build:packages` + `npm run test:ci` (scoped to extension tests) must pass before accept.
- **Rework**: Verifier produces file:line feedback; Implementer reworks; max 2 rounds per package then escalate.

## Key Risks

| Risk | Mitigation |
|------|-----------|
| Shared worker isolation weaker than process | 5 compensation layers (doc 0) + security tests (pkg 7) |
| callGate performance under load | Per-extension concurrency cap + timeout |
| Persistence migration from in-memory | bootScan compatibility + migration test |
| R1 shutdown timing | Bounded budget + forceExit fallback |
